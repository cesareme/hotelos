# API Contracts

## Route Permissions

API edge permissions are declared in `apps/api/src/security/route-permissions.ts` and enforced by a Fastify `preHandler`.

- Every registered route — `GET` included — must have an exact `method + path` manifest entry. The `preHandler` runs on public routes too, so those are declared with `permissions: []` and `riskLevel: "public"`.
- A mutation (`POST`, `PATCH`, `DELETE`) without an entry is always refused with 403.
- A `GET` without an entry is refused with 403 in strict mode. Strict mode is `RBAC_STRICT=true`, or — when `RBAC_STRICT` is unset — `NODE_ENV=production` (fail-closed by default in production; `RBAC_STRICT=false` is an explicit opt-out). Dev/demo environments stay fail-open with a logged warning per path.
- `tests/api-route-permissions-contract.test.mjs` (CI, `pnpm test`) asserts set equality between the registered routes (`server.ts`, `routes/*.ts`, template loops) and the manifest: no unmapped route, no orphan entry, no duplicate entry (lookup is first-wins), and every permission key present in `PERMISSIONS` (`packages/shared`).
- High-risk operational actions name the same permissions as the service layer.
- Critical actions such as refunds, invoice issue/cancel, journal posting, room blocking, and AI confirmation execution require high-risk or role-specific permissions.
- The manifest is additive to service-level validation; backend tools still validate business rules, property scope, confirmations, and audit events.
- `PUT` is an accepted verb (Tanda 3): it is used for idempotent overrides such as `PUT /backoffice/properties/:propertyId/taxes/rates` and fails closed like any other mutation when unmapped.
- Forced password rotation (Tanda 3 · CFG-P1-6): a session opened with a temporary password (`User.mustChangePassword`) may only call the routes in `PASSWORD_CHANGE_ALLOWLIST` (`apps/api/src/lib/auth-context.ts`: change-password, password-policy, `/users/me/*`, sessions). Any other route answers `403` with `details.code = "PASSWORD_CHANGE_REQUIRED"`; the front redirects to the change-password screen. Public routes and unknown paths (404) are not gated.
- Read keys (Tanda 5 · L1b · api-side): a `GET` never requires a write key. The families that used to be gated by `folio.charge.post` or `compliance.ses.submit` now carry their own read key — `folio.read` (`GET /folios/:id/balance`, `GET /reservations/:id/folios`, `GET /reservations/:id/routing-rules`), `pos.read` (`GET /properties/:propertyId/pos/outlets|tickets|cash-summary`), `tourist_tax.read` (`GET /tourist-tax/rates`, `GET /properties/:propertyId/tourist-tax/applications`), `billing.compliance.view` (`GET /properties/:propertyId/verifactu|tbai|igic/submissions`, `GET /verifactu|tbai|igic/submissions/:id`, `GET /invoices/:id/verifactu`) and `guest_register.read` (`GET /properties/:propertyId/guest-register-records`, `GET /properties/:propertyId/compliance/inbox`, `GET /properties/:propertyId/ses/submissions`, `GET /ses/submissions/:id`). The catalogue has 215 keys; the templates that open those screens (manager, receptionist, accountant, compliance, fnb) received the read keys additively (`docs/runbooks/rbac-sync.md`). `GET /developer/keyboard-shortcuts` was removed: the shortcut sheet reads `content/help-articles/keyboard-shortcuts.ts`.
- Boot policy (Tanda 3 · VeriFactu): `resolveVerifactuSoftware()` validates the `SistemaInformatico` block (producer NIF, `IdSistemaInformatico`, version, installation number). With `VERIFACTU_MODE` other than `sandbox` an invalid block aborts the boot (`process.exit(1)`, like AUTH-04); in sandbox it only logs a warning. `GET /health` exposes it as `checks.verifactu.software = { ok, errors }`. Estructura societaria (Tanda 6b, 2026-09-16): the `NumeroInstalacion` of every record now comes from `verifactu_installations` — the declared installation of the centre (`LegalEntity.verifactuChainScope = per_center`) or of the sociedad (`per_entity`) — and `VERIFACTU_INSTALL_NUMBER` is only the **sandbox** fallback; in `preproduction` / `production` a centre without an active installation leaves its submissions `retrying` with `errorCode = INSTALLATION_NOT_DECLARED` (never the env). The boot check of the env block is unchanged (deployment contract).

## RBAC por departamento, nivel y ámbito (Tanda 8a · L1)

Diseño: `docs/design/RBAC-DEPARTAMENTOS.md`. Una sola decisión de acceso por petición = plantilla × ámbito × módulo, calculada para la propiedad sobre la que se actúa. Fail-secure en todo: sin permiso = 403, fuera de ámbito = 404 opaco, sin asignaciones = nada.

- **`riskLevel: "authenticated"`** (nuevo valor del manifiesto): la ruta no exige ninguna clave pero SÍ una sesión real o el fallback demo explícito (`HOTELOS_ALLOW_DEMO_AUTH=true`), exactamente como `low`. Las 37 rutas no públicas que llevaban `permissions: []` (`/auth/change-password`, `/users/me*`, `/properties`, `/search`, marketplace, oauth, notificaciones, copilot…) usan este valor. El contrato (`tests/api-route-permissions-contract.test.mjs`) exige `authenticated ⇒ permissions.length === 0` y `permissions.length === 0 ⇒ riskLevel ∈ {public, authenticated}` salvo la allowlist literal **`DYNAMIC_KEY_ROUTES`** = `POST /approvals`, `POST /approvals/:id/approve`, `POST /approvals/:id/reject`, `POST /rbac/supervisor-authorizations`, `POST /rbac/pin`: su clave es dinámica (la clave `*_approve` / de solicitud del `kind`, la clave del autorizador, la contraseña del propio usuario) y la comprueba el servicio; por eso siguen siendo `high` / `critical` (el fallback demo recibe 401).
- **Ámbito por petición** (`apps/api/src/lib/rbac-scope.ts` + hook de ámbito en `server.ts`, entre el guard de contraseña y el gate de permisos): la propiedad se resuelve en este orden — parámetro `:propertyId` (path, query o `body.propertyId`) → cabecera **`x-property-id`** (≤ 64 caracteres, `[A-Za-z0-9_-]`; fuera del ámbito del usuario → auditoría `ACCESS_DENIED { reason: "out_of_scope" }` y 404 opaco; para plataforma la propiedad debe existir y se re-apunta la organización) → propiedad de la entidad resuelta por `assertEntityAccess` (la entidad SIEMPRE manda sobre la cabecera: `request.rbacScope.resolvedFrom = "entity"`) → `null` = ruta de organización. `request.userContext.permissions` se reescribe con `permissionsFor(scope, propertyId)`: con propiedad, unión de las claves de las asignaciones que la cubren; con `null`, unión de las asignaciones `legal_entity` / `organization` o, si el usuario solo tiene asignaciones de propiedad, la **intersección** de sus conjuntos (transitorio hasta `rbac:migrate-assignments`: Carmen Owner ×8 conserva sus 222 claves en rutas de organización; «Recepción en A + Contabilidad en B» queda al mínimo común). Un usuario no plataforma cuya propiedad de parámetro no está cubierta recibe el 404 opaco de la tenencia ANTES del gate (con un conjunto vacío el gate contestaría 403 y revelaría que la propiedad existe). `assignedPropertyIds` = propiedades cubiertas por alguna asignación viva (grupos, sociedad y organización expandidos); `orgScope = true` solo con asignación viva de organización / sociedad (o el fallback demo): una sesión real con la lista de asignaciones VACÍA ya no es «toda la organización» (`isPropertyAssigned`, `propertyWithinScope`, `hasEntityReadScope`); un contexto sin lista alguna (`assignedPropertyIds === undefined`: montado fuera de `loadUserContext` — jobs, scripts) conserva la organización salvo que declare `orgScope: false`.
- **Lectura dual** hasta el corte de L6: `user_property_roles` (ámbito property) ∪ `user_role_assignments` vivas (`revokedAt IS NULL AND validFrom <= now AND (validTo IS NULL OR validTo > now)`), memo por (usuario, organización) ≤ 30 s invalidado por `organizations.rbac_version` (toda escritura de roles / asignaciones / umbrales lo incrementa).
- **Auditoría** (`audit_events`, cadena hash; `GET /rbac/access-log` los pagina): `ACCESS_DENIED` en cada 403 del gate y en cada `x-property-id` fuera de ámbito, con `afterJson { missing, scopeType, riskLevel, reason }`, IP, dispositivo y correlación, **deduplicada 1/min por usuario y ruta**; `PROPERTY_SWITCHED` una vez por (sesión, propiedad); `LOGIN_FAILED` (actor y entidad = el usuario si existe, `afterJson { reason }`, IP y dispositivo, nunca el email); `ROLE_ASSIGNED` / `ROLE_REVOKED` / `ROLE_PERMISSIONS_EDITED` / `THRESHOLDS_UPDATED` / `APPROVAL_REQUESTED` / `APPROVAL_DECIDED` (también `{ implicit: true }` en aprobaciones implícitas y `privileged` para plataforma / break glass) / `APPROVAL_EXPIRED` / `APPROVAL_CONSUMED` / `SUPERVISOR_AUTHORIZED` / `BREAK_GLASS_OPENED` / `BREAK_GLASS_CLOSED` / `BREAK_GLASS_REVIEWED`. Dentro de una sesión de emergencia cada petición lleva `correlationId = bg_<breakGlassSessionId>_<corr>`.
- **`HOTELOS_DEMO_PERMISSION_UNION`** (`apps/api/src/lib/env.ts`, `productionForbidden`): único interruptor de la unión demo de permisos (`unionPermissions`); ya no depende de `NODE_ENV` ni de `HOTELOS_ALLOW_DEMO_AUTH`. `false` en el demo local: cada sesión real ve exactamente sus claves. `GET /users/me` expone `properties[].grantedPermissions` (reales de cada propiedad), `scopes[]`, `orgScope` y `breakGlassSessionId`; `GET /users/me/properties` y `GET /properties` solo devuelven las propiedades cubiertas por el ámbito (nunca toda la organización para un usuario no plataforma).
- **Cuentas de emergencia** (`status = "emergency"`): nunca entran por contraseña (403); su sesión solo es válida dentro de una `break_glass_sessions` abierta ligada al `Session` y con `closesAt > now` (si no, 401).

## Audit Integrity

Audit events and domain events are append-only records sealed by a SHA-256 hash chain in `apps/api/src/modules/audit/audit.service.ts`.

- Each audit record stores `hashAlgorithm`, `previousHash`, and `currentHash`.
- Each domain event stores the same fields so event replay can detect tampering or gaps.
- `/audit-events/integrity` and `/events/integrity` recompute the chain and return the first broken record if verification fails.
- Application code records audit/domain events through `recordAuditEvent` and `recordDomainEvent`; there are no update or delete APIs for audit records.

## Offline Sync

- `POST /offline/sync` (`ai.tool.execute`): cuerpo `{ propertyId, deviceId, actions[] }`. Tanda L2 (L2-04): cada acción aceptada, rechazada o en conflicto se persiste en Prisma `offline_sync_records` con `organizationId` (columna NOT NULL de la migración `20260918130000_persistencia_l2`) y `propertyId`; la propiedad del lote debe pertenecer a la organización del usuario y estar en su ámbito (404 opaco «Propiedad no encontrada.» antes de escribir nada). Respuesta `{ accepted, rejected, conflicts, results[] }`.
- `GET /properties/:propertyId/offline-sync-records` (`ai.tool.execute`): las 200 filas más recientes de la propiedad, filtradas por su organización (404 opaco fuera del ámbito).

Allowed offline action types:

- `housekeeping.room.clean`
- `housekeeping.task.create`
- `housekeeping.task.update`
- `housekeeping.note.create`
- `maintenance.work_order.draft`
- `maintenance.photo.pending_upload`
- `voice.command.draft`
- `confirmation.status.cache`

Rejected offline action types:

- `invoice.issue`
- `reservation.check_in.final`, unless a future explicit property policy enables it

Every accepted, rejected, or conflicted offline action is persisted as an offline sync record and audit event.

Cancelación y no-show con política (Tanda L3 · lote B + corrector ronda 1, `modules/cancellation-policy/reservation-lifecycle.service.ts`; ambas rutas `pms.reservation.modify`, high): la política de la reserva (id → código → política por defecto del centro `isDefault`; sin política = sin cargo) se aplica por defecto y la respuesta es el registro de la reserva más `cancellation { mode: cancellation | no_show, applied, charge { amount, basis: none | first_night | percent | fixed_amount | all_stay, withinFreeWindow, policyCode, policyName, label, cutoffAt }, line, folio { id, status: open | closed, balanceDue, pendingInvoice } | null, policyWaived, waivedAmount, waiver { band: T1 | T2 | above, pct, tier, authorization { mode, requestId, supervisorAuthorizationId } | null } | null }`. **Guarda de estado e idempotencia (DS-01 / FC-1 / DS-07):** solo una reserva `draft` o `confirmed` transiciona; cancelada, no_show o en casa → 409 `RESERVATION_NOT_ACTIVE` sin efecto alguno (la transición es una escritura condicional sobre el estado vivo: dos llamadas concurrentes solo cambian una fila), y la penalización es idempotente por reserva y modo (`chargeToFolio` devuelve la línea `cancellation_fee` / `no_show_fee` ya asentada en vez de una segunda). La penalización se asienta en el folio abierto de la reserva (o en uno nuevo si todos están cerrados) como línea `cancellation_fee` / `no_show_fee` con `taxCategory: "not_subject"` (indemnización, calificación N1, cuenta 705.3 sin cuota; decisión §6.4 abierta). **Cierre del folio (FC-2):** cada folio de la reserva a saldo 0 se cierra solo si todos sus cargos facturables están documentados por una factura emitida; con la penalización sin facturar queda abierto con `balanceDue: 0` y `pendingInvoice: true` (emite `POST /folios/:id/invoice` + `POST /invoices/:id/issue`: D 4300 / H 705.3 sin cuota, y ciérralo); con saldo pendiente queda abierto y `balanceDue` lo dice. Las 12 cancelaciones históricas de RA con folio abierto no se barren (decisión §6.6). Separación de funciones ANTES de escribir: una penalización > 0 exige `folio.charge.post` además de `pms.reservation.modify` (403 sin efecto alguno). **Renuncia (DS-02):** `applyPolicy: false` con penalización > 0 es un descuento del 100 % del importe renunciado y sigue los tramos del descuento de reserva (§4.7): `reason` obligatorio (400 sin motivo); ≤ T1 (importe ≤ `discount.T1` = 50 € por defecto Y ≤ `discountPctT1` = 10 % de la estancia) con `pms.reservation.discount`; ≤ `discountPctT2` (25 %) con el motor de aprobaciones `kind: discount` (solicitud aprobada de otra persona, `pms.reservation.override` propio dentro de su tramo, PIN de supervisor vía `supervisorAuthorizationId` o sesión privilegiada); por encima solo solicitud aprobada (sin PIN) → 409 `APPROVAL_REQUIRED { kind: discount, tier }` sin escribir nada. Se audita como `RESERVATION_CANCELLATION_POLICY { policyWaived: true, waivedAmount, waiver }` más las auditorías del motor (`APPROVAL_DECIDED` / `APPROVAL_CONSUMED`). Vista previa sin escribir: `GET /reservations/:id/cancellation-charge?mode=cancellation|no_show` (`pms.reservation.read`; `mode` omitido = `cancellation`) devuelve el mismo `charge`; la ventana gratuita se mide a las 14:00 hora del hotel (`Property.timezone`) del día de llegada (`cutoffAt`). El cierre del día aplica el no-show automático con la misma orquestación (`processNoShows`; el actor deriva `pms.reservation.modify` de `night_audit.run` solo para ese paso). **Rutas heredadas (DS-03)** `POST /reservations/:id/apply-cancellation-fee` · `/apply-no-show-fee` (`folio.charge.post` + `pms.reservation.modify`): reparación de una penalización que no llegó a asentarse; exigen que la reserva YA esté `cancelled` / `no_show` (409 `RESERVATION_STATUS_MISMATCH { status, expected }` en cualquier otro estado) y son idempotentes (`{ breakdown, line | null, alreadyApplied }`), nunca abren un folio secundario. El front (ficha de reserva) levanta el 409 de la renuncia con el PIN de supervisor (`SupervisorPinDialog`, clave `pms.reservation.override`, entidad `reservation`) y reenvía la misma llamada con `supervisorAuthorizationId`.

Every mutation writes an audit event. Reservation create, room assign, check-in, check-out, cancel, and no-show also write domain events.

Availability quotes return only room types, availability, prices, and policies calculated by the backend tool.

Las herramientas high|critical y las que exigen un rol de aprobación requieren además `ai.high_risk.confirm` (403 `AI_TOOL_CONFIRM_FORBIDDEN`). Una fila pendiente de más de 24 h responde 409 `AI_CONFIRMATION_EXPIRED` y pasa a `rejected`. 404 «Llamada de herramienta no encontrada.» con id inexistente, de otra organización, de otra propiedad, ya reclamado o que no espera confirmación. Al cerrar la fila, `input_json` y la propuesta se persisten redactados (sin PII). Toda escritura de las 25 herramientas con `execute` queda en `awaiting_confirmation`; las lecturas y borradores se ejecutan al instante. Presupuesto mensual agotado → 403 `AI_BUDGET_EXCEEDED` (`propertyId`, `budgetEur`, `spentEur`); límite por organización → 429 `AI_RATE_LIMITED` (`details.retryAfterSeconds`). `ai_tool_calls.status` ∈ `succeeded | failed | pending | awaiting_confirmation | rejected | completed | skipped`; `cost_eur` es 0 solo cuando no hubo llamada al modelo y NULL cuando la hubo sin `usage` o sin `AI_USD_EUR_RATE`. `GET /health` expone `checks.ai` (proveedor, modelos, presupuesto por defecto, rate limit; nunca la clave).

Guest register records retain required extracted fields and signature references, not ID images. Failed SES records can be corrected and requeued with audit events.

### Listas, N+1 y catches (L2-05 · L2-06)

Convención de listas (decisión §6.12, Tanda L3 · lote E; `lib/pagination.ts`): toda lista con cursor responde por defecto un **array plano** y SIEMPRE las cabeceras `X-Total-Count` / `X-Next-Cursor`; el envelope `{ items, total, nextCursor }` solo se devuelve cuando el cliente lo pide con `?cursor=` o `?envelope=1` (así lo hacen `GET /properties/:propertyId/invoices`, `GET /properties/:propertyId/reservations`, `GET /events`, `GET /ai/tool-calls` y `GET /properties/:propertyId/ses/submissions`; `GET /fiscal/vat-books` conserva su objeto `{ rows, resumen, origen, avisos, periodo, total, nextCursor }` con las mismas cabeceras). Las listas acotadas sin cursor (`GET …/pos/tickets` con `limit` ≤ 500, `GET …/pos/cash-closures`, `GET /approvals`) devuelven un array; el motor genérico (L2-03) y `GET /admin/worker/job-runs` devuelven su objeto `{ items, total, … }` documentado arriba. Ningún consumidor del front (`apps/admin-web`, `payment-flow`, `BillingCenter`) lee un envelope que no haya pedido; los `take` de L2 siguen en su sitio. Los 17 bucles N+1 pasaron a consulta agregada con resultado idéntico. Ningún `catch` en runtime traga en silencio: los servicios de KPI pasan por `createDegradedCollector` (`lib/degraded.ts`, 15 ficheros: dashboards, `/search`, `POST /copilot/ask`…) y nombran en `degraded: string[]` (campo ADITIVO) la consulta que falló; el money-path lanza errores tipados (`details.code = ACCOUNTING_LINK_FAILED` con `correlationId` en `accounting/projection.ts`; un P2025 simulado deja la proyección `posted` y solo avisa).
